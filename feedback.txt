FEEDBACK: What was built, in what order, and what was observed

Plain, honest account of the build and testing process.

## 1. What was implemented and in what order

The build followed the stages in the build prompt in order.

Stage 1 (research) was completed first and the verified values were written to
NETWORK_CONFIG.md. Stage 2 and 3 (contract) came next. Stage 4 (tests) was written and run
until green. Stage 5 (deployment config) and the frontend configuration were done next.
Stages 6, 7 and 8 (wallet, design system, pages) were implemented together in the frontend.
Stage 9 (verification) was performed at the end.

The stack is as specified: React + Vite, viem for all reads and writes, Reown AppKit as the
fallback wallet path, Tailwind CSS with the custom palette, Framer Motion for animation,
Solidity 0.8.24 via Foundry, and OpenZeppelin for SafeERC20 and ReentrancyGuard. No backend
server or database.

## 3. Deviations from the specification

- The `latePayments` mapping is tracked and written only where required (it is incremented
  nowhere in the current logic because no grace period logic exists, which matches the
  spec's instruction to reserve it for future use). It is exposed as a public read.
- Two extra fields were added to the Invoice struct that the supplementary document
  required: `sellerHasClaimed` (explicitly required by A.6) and, additionally,
  `distributedAmount` and `claimsMade`. These last two are needed so that `sweepDust` can
  know how much genuine leftover remains and when all claims are settled, as described in
  A.3. These are flagged as necessary additions.
- `sweepDust` uses a slightly adjusted expected-claim count for defaulted invoices: on a
  default the seller cannot claim, so the expected count is the number of investors (not
  investors plus one). This prevents the edge case where a defaulted, staked invoice with no
  investors would otherwise leave the stake permanently locked.
- The platform was deployed to BOT Chain Testnet during a later run once a funded private key
  became available (see section 6). The deployment script is complete and documented, and the
  live address is recorded in NETWORK_CONFIG.md and placed in the frontend config.
- The Reown AppKit dependency required careful version pinning to build. Details below.

## 7. Judgement calls and dependency issues

The single most time-consuming issue was the frontend dependency graph. The Reown AppKit
wagmi adapter in the current registry snapshot resolves to @wagmi/connectors v8, which is
tied to wagmi 3 and imports a viem subpath (viem/tempo/zones) that does not exist in the
stable viem 2.x line. That made a plain install fail to build. After exploring several
combinations, the working solution pins wagmi 2.19.5, @wagmi/core 2.22.1, viem 2.56.0, and
forces @wagmi/connectors to 6.1.0 via an npm override, alongside Reown AppKit 1.8.23. This
set builds and runs cleanly while preserving the required primary (injected) and fallback
(AppKit) wallet paths. The pinned versions are recorded in frontend/package.json.

Two mainnet-capability verifications that were part of Stage 1 (USDT decimals and symbol)
were done via direct RPC calls rather than the explorer's verified-contracts page, because
the explorer's USDT page did not render verified contract metadata. The RPC results are
authoritative for the token and match the bridge documentation.

## 8. The gas estimation bug and its actual cause

Reported symptom: claiming a username failed because the wallet could not estimate gas.

Root cause, in frontend/src/hooks/useInvoiceFactory.js. The retry helper destructured its
parameters with `const { address, abi, functionName, args, value } = params`. That local
`address` is the contract address, and it shadowed the outer `address` returned by
useAccount(). The next line passed `account: address` into publicClient.simulateContract, so
every simulation ran as though the InvoiceFactory contract itself were the caller.

For claimUsername that means the simulated call executes
safeTransferFrom(msg.sender = the contract, feeRecipient, 1 USDT). The contract holds no USDT
and has granted itself no allowance, so it reverted with ERC20InsufficientAllowance. The
helper retried three times, then surfaced a gas error.

This was never specific to USDT or to claimUsername. It broke every write path in the
application, including confirmInvoice, payDirect, tokenizeInvoice, invest, repayTokenized,
markDefault, all three claim functions and sweepDust. claimUsername was simply the first place
it was noticed.

Reproduced and then disproved directly against the live contract:

  simulate as the contract  -> reverts, selector 0xfb8f41b2
                               ERC20InsufficientAllowance(spender=<factory>, allowance=0,
                               needed=1000000)
  estimate as the contract  -> same revert, no gas figure available
  simulate as the user      -> succeeds
  estimate as the user      -> 113833 gas

The transaction layer was rewritten rather than patched. What it now does:

- Simulates with the connected account, and never with the contract address.
- Sends an explicit gas limit taken from the simulation plus 25 percent. Several wallet
  in-app browsers show a blank or dashed fee and refuse to sign when their own estimation
  call fails, so the limit is supplied rather than left to them.
- Polls the ERC20 allowance after an approval is mined until the node actually serves the new
  value. Waiting on the receipt alone is not enough behind a load balanced RPC, where the
  next read can land on a node one block behind and report the stale allowance. That stale
  read was a second, independent cause of the same visible failure. The previous code slept
  300 ms and hoped.
- Checks the USDT balance before raising an approval prompt, and checks the native BOT balance
  against the gas cost before opening the wallet, so a shortfall is explained in advance
  instead of failing mid-flow.
- Waits for the receipt and checks its status before reporting success anywhere in the UI.
  The previous code toasted success on submission and refetched after a fixed 1500 ms.
- Maps every custom error in the contract to a specific sentence. Retries are limited to
  genuinely transient RPC conditions and never to reverts.

Every USDT-spending path now goes through one function, `c.call(fn, args, { approve })`, so
the approval, balance check, gas budget, simulation and receipt wait cannot be forgotten on a
new call site. The four paths that pull USDT are claimUsername (1 USDT), payDirect and
repayTokenized (face value), tokenizeInvoice (stake) and invest (contribution). Create invoice
was also moved onto this path; it previously called wagmi's writeContractAsync directly with
no simulation at all.

## 9. Wallet layer defect

main.jsx built a wagmi config with createConfig and handed that to WagmiProvider, while
createAppKit was given a WagmiAdapter holding a completely separate config. AppKit wrote a
connected session into the adapter's config and every hook in the application read from the
other one. The mobile and WalletConnect path therefore appeared to do nothing at all:
useAccount never saw the connection.

Fixed by making the AppKit adapter the single source of truth. lib/chain.js creates the
adapter and exports adapter.wagmiConfig, which is what WagmiProvider now receives.

Three further wallet issues were fixed at the same time:

- connect() was called without await and navigate("/dashboard") ran before the connection
  resolved. Now uses connectAsync.
- Only one injected provider was offered. Wallets are now discovered through EIP-6963 and
  listed individually by name and icon, with the generic injected connector as a fallback for
  older extensions and wallet in-app browsers that do not announce themselves.
- The wrong network banner was displayed but nothing was gated. Write actions stayed enabled
  and could be signed against the wrong chain. Signing is now blocked in the transaction
  layer and every action button is disabled with an explanation, while read-only browsing
  continues to work as the specification requires.

## 10. Contract defects found and fixed

The contract had to be redeployed because it is immutable by design. Three defects:

1. On a partially sold invoice that defaulted with a stake, claimInvestorShare divided by
   10000 rather than by the sold percentage. With 40 percent sold and a 20 USDT stake,
   investors could claim only 8 USDT between them. The remaining 12 USDT then met the
   preconditions of sweepDust and was transferred to the platform fee recipient as though it
   were rounding dust. A seller's first-loss buffer partly became platform revenue.

   Fixed by recording a distribution basis on the invoice at settlement. It is 10000 on a
   normal repayment, preserving the existing behaviour exactly, and totalSoldPercentageBps on
   a default, so the whole stake is shared between investors in proportion to what each bought
   relative to one another. Verified live: 40 percent sold, 20 USDT stake, investors received
   15 USDT and 5 USDT, sweepable dust 0.

   A related edge case surfaced while fixing this. If an invoice was tokenized with a stake but
   attracted no investors, the old code still consumed the stake, leaving it claimable by
   nobody and eventually sweepable to the fee recipient. The stake now stays intact in that
   case and returns to the seller, because there was never anyone for it to protect. This is a
   deliberate deviation from supplementary clarification A.4, which assumes the stake was
   fully consumed covering investors. That premise does not hold when there are none.

2. _checkAndGrantTrusted re-emitted TrustedStatusGranted on every repayment once the
   thresholds were met, rather than once. Section 3.4 of the prompt says to emit only if not
   already granted, and there was no state to check against. Added an isTrusted mapping,
   written only by that internal function, which also gives the frontend a single read instead
   of deriving the badge from two counters in three separate places.

3. sweepDust reverted with AlreadyClaimed when claims were still outstanding, which says the
   opposite of what happened. Added ClaimsPending(settled, expected). sweepDust also now
   rejects an unsettled invoice outright instead of relying on the leftover being zero.

Accounting was tightened alongside these. A poolAmount field records what the contract holds
for an invoice's claimants, which is the net repayment plus any still locked stake. sweepDust
computes the leftover from that rather than from repaidAmount, which had understated the pool
on a repaid invoice that carried a stake. InvoicePaidDirect now emits the gross face value,
matching InvoiceRepaid; it previously emitted the net figure in the same argument position.

Also added, all view only and none of them privileged: getInvoice returning a named struct,
getInvoices for paged reads, getInvestors, investorCount, getCreditProfile,
claimableInvestorShare, claimableSellerShare, sweepableDust and quoteInvestment. These exist
so the frontend can show a claimable balance or an investment preview using the contract's own
arithmetic instead of reimplementing it in JavaScript, where it could drift.

## 15. Known limitations that remain

- The frontend still reads the entire invoice book to build the marketplace, dashboard and
  profile pages. The contract's new paged getter reduces this from one request per invoice to
  one per fifty, which is a large improvement but not a solution. Investor positions still
  require one read per invoice per address, because the contract has no reverse index from an
  investor to their invoices and adding one is not worth the write cost at this scale. An
  indexer or a subgraph remains the correct answer for production.
- Contract source verification: this was initially recorded here as impossible without a
  Blockscout API key. That was wrong. The Blockscout instance at scan.bohr.life accepts
  verification with no API key, and the live contract is now verified:

    forge verify-contract 0x1e6c1FD4a91Eefd68b22d70574d263FBe617a7be \
      src/InvoiceFactory.sol:InvoiceFactory --chain-id 968 \
      --verifier blockscout --verifier-url https://scan.bohr.life/api/ \
      --constructor-args $(cast abi-encode 'constructor(address,address)' <usdt> <feeRecipient>) \
      --watch

  Confirmed by reading it back from the explorer API: ContractName InvoiceFactory, compiler
  v0.8.28+commit.7893614a, optimization enabled, 34873 characters of source and a full ABI
  published. Anyone can now read the contract they are trusting. The earlier deployment
  remains unverified and is superseded.
- Browser testing was performed after this section was first written, using headless Chromium
  driven over the DevTools protocol. See section 16. Testing on real device hardware still has
  not happened, and touch behaviour, the home indicator inset and wallet in-app browsers cannot
  be confirmed from a headless run.
- The activity backfill previously asked for a 300000 block window in a single getLogs call,
  which public RPC nodes commonly refuse. This has been fixed: history is now walked backwards
  from the newest block in 10000 block chunks, stopping once roughly a screenful of events has
  been gathered. A chunk that a node still refuses is skipped rather than aborting the walk, so
  one bad range can no longer empty the whole feed, and the loading state is released after the
  first chunk lands so the rest streams in behind it.
- latePayments is still never incremented. There is no grace period logic, so there is nothing
  to distinguish a late payment from a default. It remains reserved, as the specification asks,
  and is displayed as a zero rather than hidden.
- The first deployment's invoice history is orphaned. Nothing can migrate it.
- contracts/.env still holds a funded private key. It is gitignored. Do not reuse that key for
  anything of value.

## 16. Headless browser verification

Added after the sections above, because reporting the interface as unverified when it could be
checked was not good enough.

frontend/verify-browser.mjs drives headless Chromium over the DevTools protocol using Node's
built-in WebSocket, so it needs no extra dependencies. For each of the ten routes at 375, 768
and 1440 pixels wide it records uncaught exceptions, console errors and failed network
requests, asserts that React actually mounted and painted, checks for horizontal page scroll,
and captures a screenshot. Run it with the preview server on port 4173 and Chromium listening
on port 9222; the commands are in steps.txt.

Result across 30 route and viewport combinations: 0 render failures, 0 blank pages, and no
horizontal page scroll anywhere. document.scrollWidth equalled the viewport width at every
size. Live contract data rendered correctly, which also confirms the frontend reads the
redeployed contract's changed struct: invoice 1 showed face value 100.00, recovery pool 20.00,
40 percent sold, an implied gross yield of 25.00 percent, stake status consumed to cover
investors, and the Defaulted state labelled as text beside its colour rather than by colour
alone.

Three findings, all fixed:

1. A 404 on every page load. public/favicon.svg existed but was the unmodified Vite scaffold
   logo and index.html never referenced it, so browsers requested /favicon.ico and got
   nothing. Replaced with a project mark and wired up, along with theme-color, color-scheme,
   a description, and viewport-fit=cover for safe area insets.
2. The three credit stat tiles on the public profile were cramped at 375 pixels, with
   "On-time payments" wrapping to two lines against a single-line "Defaults". They now stack
   vertically below the sm breakpoint, which is what supplementary clarification B.3 asked for
   in the first place and had been missed.
3. public/icons.svg was unreferenced scaffold and was removed.

4. The horizontally scrolling tab strip used negative inline margins to bleed to the screen
   edge on phones, which made its ancestors report a scrollWidth 16 pixels wider than their own
   clientWidth. This produced no scrollbar and no visible breakage, confirmed by
   document.scrollWidth matching the viewport at every size, so it was a latent fragility rather
   than a live bug: it would have surfaced as an unwanted scrollbar the moment any ancestor was
   given overflow-x other than visible. The bleed was removed and the row now scrolls inside the
   content padding. A re-run reports no overflowing elements at all.

Network behaviour was measured separately, because the first run showed failed requests that
needed explaining rather than hand waving. Over a sequence of navigations the only failures are
localhost ERR_ABORTED, which is the application's own in-flight asset and RPC requests being
cancelled when the route changes, and is expected. Every external host succeeds:
rpc.bohr.life 12 of 12 requests, fonts.googleapis.com and fonts.gstatic.com, and
api.web3modal.org. There are no failed contract reads. The occasional ERR_TIMED_OUT seen when
hammering thirty navigations in sequence is one of those third party hosts under load, not a
defect in this application, and nothing in the interface depends on it.

One console error is not ours and is not fixable from here: Reown AppKit's analytics SDK logs
"TypeError: Failed to fetch" when its outbound telemetry request does not complete. It appeared
once in thirty page loads and not at all in an isolated run, it is caught inside that SDK, and
it has no effect on wallet connection or on any contract interaction. features.analytics is
already set to false and api.web3modal.org is otherwise reachable, so this is that SDK's own
retry noise.

What a headless run still cannot tell you, and why steps.txt section 7 still matters: whether
touch targets feel right under a thumb, whether the tab bar clears a real home indicator, and
whether a wallet in-app browser signs cleanly. That last one is where the original gas bug
lived, and it is the one case a desktop browser will not reproduce.
